Y Space: embedded-browser agent workspace and integrations

Fork Poracode as Y Space, preserve compatibility-sensitive internals, make the embedded tabbed browser the single agent-controlled browser, add safe cookie import and Pipedream Connect, and prove Codex, Claude Code, and OpenCode on the macOS desktop app.

01 · Fast answer

The upstream already solves much of the original browser request. The implementation should deepen and secure it, not replace it.

Reuse

Keep the existing tab strip, persistent Electron partition, BrowserPanelManager, browser MCP, provider adapters, MCP OAuth service, encrypted storage, and plugin/skills projection.

Change

Add caller-owned tab selection/search, make embedded browser capabilities universal, convert the external-browser bridge to cookie-import-only, and add Pipedream connections.

Compatibility boundary

Brand the product as Y Space in user-facing surfaces while retaining Poracode/Lightcode internal identifiers, migrations, protocols, data paths, and persistent browser partition.

Resolved decisions

1A · Fork

Public fork zvone187/y-space, master branch only.

2C · Rebrand

User-facing Y Space rebrand; preserve compatibility-sensitive internals.

3A · Cookies

Extension-assisted Chrome-family import with preview and JSON/Netscape fallback.

4A · Capabilities

Embedded browser, app controls, and core skills default-on; no agent-facing external-browser controls.

5A · Pipedream

End-user MCP preset plus local BYO Connect and secure relay using four supplied env variables.

6A · Providers

Repair/update local CLIs and test Codex, Claude Code, and OpenCode with multiple available models.

02 · Existing implementation

Observed on fork base 8e8880a8.

Reusable browser architecture
  • BrowserPanelManager, BrowserTab, and the browser renderer already implement multiple tabs, navigation, persistence, groups, history, bookmarks, panel/overlay/window placement, and headless automation lifetime.
  • BrowserTabStrip.tsx already provides Chrome-like activation, close, reorder, and tab grouping.
  • The browser MCP already exposes tab overview/create/activate/close, navigation, snapshots, DOM actions, screenshots, console/network, cookies/storage, frames, and injection tools.
  • persist:lightcode-browser intentionally preserves browser sign-ins. It must remain unchanged under decision 2C.
Reusable provider and skills architecture
  • spawnPipeline.ts is the provider-neutral launch boundary for Codex, Claude Code, OpenCode, browser MCP, Crossagents, Computer Use, app controls, and user MCP servers.
  • Codex app-server, Claude Agent SDK/CLI, and OpenCode SDK/TUI adapters already support models, modes, approvals, resume, and MCP translation.
  • SkillsService already discovers and projects skills into provider-native roots; core Y Space skills can reuse this mechanism.
  • App-controls MCP already exposes projects, tasks, settings, files, terminals, agents, git/GitHub, MCP servers, skills, notifications, and schedules.
Reusable Pipedream/MCP architecture
  • McpOAuthService already implements discovery, DCR, PKCE, refresh, encrypted token storage, system-browser authorization, and loopback callbacks.
  • User MCP translation already covers Codex, Claude, OpenCode, ACP, Gemini, and Cursor.
  • secretStorage.ts, authenticated localhost ingress patterns, and supervisor lifecycle wiring provide the primitives for a safe Pipedream relay.
Gaps to close
  • Browser MCP is not enabled for every agent by default.
  • Browser tools without an explicit tab use one global active tab, so concurrent agents can collide.
  • Tab groups suggest ownership but tab metadata does not directly encode owner, creator, or last use.
  • OpenCode provider-level MCP drops normal thread identity; its current trusted hook only repairs Crossagents routing.
  • No browser-cookie import workflow exists.
  • The existing Chrome MCP gives agents control over a real external browser, contrary to the resolved embedded-only product direction.
  • No first-party Pipedream connections catalog/account manager/relay exists.

03 · Libraries and services

No new runtime packages are planned initially.

The current Electron, MCP SDK, Zod, HTTP/fetch, SQLite, and encrypted-storage primitives are sufficient. Add a dependency only if implementation evidence shows the existing stack cannot meet a specific requirement.

External APIs used
  • Pipedream end-user MCP: https://mcp.pipedream.net/v2.
  • Pipedream Connect OAuth, apps, accounts, Connect Link, and developer MCP /v3.
  • Electron session cookies for controlled import into the embedded persistent partition.
  • Chrome WebExtension cookies API solely for user-initiated cookie export/import—not agent control.

04 · New implementation

Work is divided into five independently testable vertical slices.

A. Y Space surface and Codex-like shell
  • Replace user-visible Poracode/Lightcode labels, descriptions, onboarding, menus, about screens, settings, website copy, browser tool text, extension copy, and bundled skill language with Y Space.
  • Preserve internal app IDs, environment names, package scopes, filesystem paths, protocols, migration files, and persist:lightcode-browser.
  • Refine spacing, sidebar hierarchy, thread header, composer, right-panel chrome, typography, neutral surfaces, and activity presentation against the current Codex desktop visual language.
  • Use existing design tokens/components; avoid a parallel component system.
B. Embedded browser as the sole agent browser
  • Add versioned tab metadata: ownerThreadId?, createdBy, and lastUsedAt.
  • Add a caller workspace registry that tracks selected tab and automation leases by trusted thread/provider session and MCP session.
  • Resolve implicit tab targets in this order: explicit tab ID → caller-selected tab → newest caller-owned tab → new caller-owned tab. UI-only calls may use the global active tab.
  • Add find_tabs and open_or_focus_tab; enrich list_tabs with ownership and caller-selection metadata.
  • Make background agent tab activation avoid stealing the user’s visible focus unless reveal:true.
  • Pass trusted identity through every provider. For OpenCode, generalize provider-session metadata injection or issue a per-session authenticated local browser endpoint that maps directly to a Y Space thread and fails closed.
  • Default the embedded browser core plugin and core browser skill on for new and existing settings, with a global kill switch. Keep cookie/storage and eval gates off by default.
  • Remove the external Chrome MCP from agent launch configuration, composer/settings affordances, and core capability defaults. Retain only the import bridge described below.
C. Cookie import into the embedded profile
  • Refactor the companion extension/localhost bridge into an import-only cookie source. It must not expose debugger, tab-control, CDP, DOM, or navigation commands to agents.
  • Support Chrome, Brave, Edge, and Arc extension profiles; allow more than one paired source connection.
  • Add a main-process BrowserCookieImportService. The renderer receives source/profile/domain/name/count/status metadata but never cookie values.
  • Flow: connect source → preview domains/counts → select domains → confirm → import to the embedded session → flush cookie store → show imported/skipped/failed counts.
  • Validate domain/path, expiry, secure, httpOnly, SameSite, host-only semantics, and source profile. Skip expired, malformed, partitioned/CHIPS, and unsupported container cookies with explicit reasons.
  • Add Cookie-Editor JSON and Netscape cookies.txt file import as the Firefox/Safari fallback.
  • Never log, render, separately persist, or expose raw cookie values to agents. Imported cookies become ordinary embedded-profile cookies governed by the existing data-access gate.
D. Pipedream connections
  • Add a first-party “Connect Pipedream” preset using end-user MCP v2 and the existing MCP OAuth flow.
  • Add a Connections settings page and supervisor-owned PipedreamConnectService for app search, Connect Link, account list, binding, and disconnect.
  • Read PIPEDREAM_PROJECT_ID, PIPEDREAM_ENVIRONMENT, PIPEDREAM_CLIENT_ID, and PIPEDREAM_CLIENT_SECRET from the process environment for development; never expose values through renderer IPC or agent configuration.
  • Generate one opaque install-scoped external-user ID. Never derive it from project, thread, email, or agent ID.
  • Keep developer access tokens in supervisor memory with expiry slack and refresh deduplication.
  • Expose one authenticated loopback MCP relay per bound app/account. Strip inbound Authorization and all agent-supplied x-pd-* headers, then pin project, environment, external user, app, and account server-side.
  • Inject only the loopback URL and random local bearer into Codex, Claude, and OpenCode. Preserve tool annotations and existing approval behavior.
E. Provider capabilities and skills
  • Create one provider-neutral Y Space core capability bundle: embedded browser, app controls, core skills, Crossagents, and enabled Pipedream bindings.
  • Install canonical core skills under the shared skill root and project them into Codex, Claude, and OpenCode native roots during launch preparation.
  • Add a concise browser baseline instruction: inspect existing tabs first, search by title/URL, reuse when appropriate, and create a caller-owned tab otherwise.
  • Make OpenCode plugin installation/readiness observable. Do not advertise identity-dependent capabilities when the trusted hook/proxy is unavailable.
  • Keep Computer Use available but permission-gated; it is not the browser path.

05 · Refactoring and cleanup

Split browser responsibilities

Extract caller workspace/lease state and cookie import from the already-large BrowserPanelManager.

Retire external control

Delete agent-facing Chrome MCP translation, tools, toggles, and launch wiring while retaining a narrowly scoped import bridge.

Generalize trusted identity

Replace Crossagents-only OpenCode routing assumptions with a reusable provider-session capability boundary.

Separate secrets from settings

Never put Pipedream credentials/tokens into plaintext shared settings; keep renderer contracts status-only.

06 · Tests and user stories

User stories
  • As a user, I can create, reorder, activate, group, close, and restore several embedded browser tabs.
  • As a user, I can tell any connected agent about an existing tab and it can find, focus, inspect, and operate that exact tab.
  • As a user running concurrent agents, each agent keeps its own selected/owned browser workspace without controlling another agent’s implicit target.
  • As a user, I can import selected logged-in domains from Chrome or Brave into Y Space without exposing cookie values to the UI, logs, or agents.
  • As a user, I can connect Pipedream, add app accounts, use read-only tools from any provider, select the intended account, and disconnect cleanly.
  • As a user, I can run Codex, Claude Code, and OpenCode with available models and receive the same Y Space browser/skills/integration capabilities.

Acceptance criteria
  • All user-visible product surfaces say Y Space while compatibility-sensitive internal identifiers and stored sessions remain intact.
  • Every supported desktop agent receives embedded browser and core skill capabilities by default; no agent receives an external-browser MCP.
  • Agents can list/search/open-or-focus tabs, and concurrent agents maintain independent implicit targets.
  • Cookie import requires user action and preview; raw values never cross renderer IPC or appear in logs; an imported login survives restart.
  • Pipedream secrets never reach renderer/shared settings/provider configs; real account state and relay headers prove the intended user/app/account route.
  • Codex, Claude Code, and OpenCode each complete browser and Pipedream read-only smoke tasks on at least two available model configurations where account access permits.
  • Automated suites, type checks, lint, formatting, packaging smoke, and manual macOS UI workflows pass with captured evidence.

08 · Risks and mitigations

Cookie secrecy

Values could leak through IPC/logs. Keep values main-only, use metadata DTOs, redact errors, and add canary-secret tests.

Agent tab races

Global active-tab fallback can target the wrong page. Require trusted caller identity for agent calls and isolate selection/leases.

OpenCode pooled server

Provider-level MCP can lose thread identity. Fail closed unless a verified provider-session mapping or per-session local credential exists.

Pipedream developer secret

A desktop binary cannot safely embed a publisher secret. This plan implements local BYO credentials; a distributed product would require a Y Space backend.

OAuth/live-account dependency

Real E2E depends on Pipedream account permissions and Claude login. Separate implementation correctness from credential-dependent QA and capture both statuses.

Compatibility naming

Surface rebrand can accidentally rename internal identities. Maintain an explicit allowlist of compatibility identifiers and test persisted data/session paths.

09 · Assumptions and deferred items

  • The four supplied Pipedream variables are development credentials for the fork owner’s local testing and will remain ignored/uncommitted.
  • Chrome and Brave provide the primary live extension-import QA; Firefox/Safari use file fallback in this release.
  • Computer Use remains a separately permissioned capability, but it is not used as a substitute for the embedded browser.
  • Publishing a shared production Pipedream backend, app-store signing/notarization, and Safari Web Extension packaging are deferred.
